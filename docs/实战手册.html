1. 项目介绍：让知识问答接上业务处理

1.1 一个贯穿全书的场景

IT 员工连接 VPN 出现 E809 错误。他先查询公司操作手册，系统只检索这个员工有权访问的文档，展示处理建议和引用原文。问题仍未解决时，员工选择准备工单，检查草稿后确认。IT 处理员接单、评论、填写解决说明，员工评价并关闭工单。

这条链路包含两个不同目标：知识助手帮助用户找到信息，工单系统把未解决的问题交给具体的人处理。AI 不应自行决定部门权限，也不应仅凭生成一句“已提交”就算创建了工单。

1.2 功能与角色

1.3 当前能力边界

已经实现真实的 LangChain 模型适配、LangGraph 状态图、PostgreSQL checkpoint、Redis Streams 入库和 Java 事务工单。2026-10-26 的验收使用明确标识的“仅检索”模式，没有调用真实云聊天或 Embedding 模型。云端连通性、生成质量、向量召回质量和费用仍需配置后单独验证。

这是适合本机学习与演示的单 Java 进程版本。已有聊天历史不等于已经实现多轮语义记忆；当前每次问答重新检索，旧助手正文不会作为模型上下文输入。没有自动规划型多 Agent、SSE、OCR、Elasticsearch、Reranker 或生产集群压测。

2. 架构与技术栈：谁负责什么

2.1 三条链路

问答链路：浏览器 → Java 验证身份与会话 → 计算文档白名单 → Python 图检索 → LangChain 调用模型或返回检索原文 → Java 再校验来源 → 浏览器展示。

入库链路：浏览器上传 → Java 验证管理权限 → Python 保存 S3 原件并登记任务 → Redis Streams → worker 解析、切块、向量化 → PostgreSQL 发布当前版本。

工单链路：图准备草稿 → interrupt 暂停 → 人工确认 → Java 事务创建工单 → Python Command(resume=...) 恢复 → 处理员处理 → 员工评价关闭。

2.3 为什么保留 Java，再引入 Python

Java 负责稳定的身份与业务规则，Python 使用 LangChain/LangGraph 组织模型能力。二者通过内部 HTTP 契约协作。这样学习时能明确区分“模型建议”和“业务事实”：模型可以生成解释，工单是否存在必须以 Java 事务结果为准。

代价是多一个服务、多一次网络调用和跨服务一致性问题。若只做小型 Python 产品，完全可以采用 FastAPI 单体；本项目保留两种语言，是为了同时练习 Java 业务工程与 Python AI 应用开发，而不是声称微服务天然更好。

2.4 数据分区

同一个 PostgreSQL 实例中，Java 的 hd_* 表在 hd_business schema；Python 索引、任务与确认回执等 ai_* 表在 public；LangGraph 库自己的 checkpoint 表在 ai_graph。checkpoint 表保留库的原生名字，不强行加前缀。

这能避免 Python 先建表后，Flyway 因 public 已非空而误判业务数据库初始化状态。schema 隔离解决的是结构归属，不代表 Java 与 Python 的 HTTP 操作自动进入一个分布式事务。

3.3 配置聊天模型与 Embedding

聊天模型负责“根据证据组织答案”，Embedding 模型负责“把文本映射到向量用于相似度检索”。它们是两种不同的能力，不是填写一个聊天模型名就自动拥有向量服务。

只在本机 ai-service/.env 填写以下配置；这里展示的是占位符，不是可直接使用的凭据：

AGENT_LLM_API_KEY=你的Key
AGENT_LLM_MODEL=账号有权使用的聊天模型名
AGENT_LLM_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
AGENT_EMBEDDING_MODEL=text-embedding-v3
AGENT_EMBEDDING_DIMENSIONS=1024

切换供应商时同时核对接口地址、聊天模型和 Embedding 支持情况。Embedding 默认复用聊天 Key 与地址，也可单独设置 AGENT_EMBEDDING_API_KEY、AGENT_EMBEDDING_BASE_URL。1024 维必须与当前数据库列和客户端一致。

修改配置后重启，再看系统状态。modelConfigured 表示配置字段齐全，不代表已经成功连接供应商。之前按关键词模式入库的文件，需要通过“更新版本”重新上传，才会补做 Embedding。只重启不会自动给历史分块生成向量。

4. 登录与权限：先确定谁有权，再决定给模型什么

4.1 登录不是 JWT

本项目采用随机不透明 Bearer token。AuthService 验证 BCrypt 密码后生成 256 位随机令牌，数据库保存令牌的 SHA-256 摘要和 12 小时有效期；浏览器保存原始令牌用于请求，退出时服务端删除令牌记录。

BCrypt 用于慢速验证人类密码，降低离线猜测效率；随机令牌具有足够熵，可以保存快速摘要以避免数据库直接持有可用登录令牌。不要把“密码哈希”和“会话令牌摘要”混为一谈。

前端使用 sessionStorage。它有页面会话生命周期上的便利，但不能抵御同源 XSS，因此仍需正确渲染不可信内容、控制脚本来源。当前身份方案便于撤销会话，代价是请求需要查验服务端会话状态。

4.2 权限同时看角色、部门与资源归属

RBAC 回答“这个角色能否做此类操作”，资源规则回答“能操作哪一条”。例如 AGENT 可以管理文档，但只能管理本部门文档；EMPLOYEE 可以查看工单，但只能看自己创建的工单。

TicketService.java 中真实的可见性判断为：

return actor.role == Role.ADMIN
    || t.creatorId.equals(actor.id)
    || (actor.role == Role.AGENT
        && t.departmentId.equals(actor.departmentId));

前端隐藏按钮只是改善体验。真正的边界在 Java 服务层；即使手工调用 HTTP 接口也必须得到同样的拒绝结果。也不能把工单管理员权限推导成会话管理员权限，会话规则更严格。

4.3 模型不能给自己授权

浏览器提问只提交 question 和 requestTicket。userId、role、departmentId、allowedDocumentIds 由 Java 根据登录身份计算，再发送给 Python。Python 还会用索引元数据的部门、可见性、版本与 READY 状态交叉检查。

所有 /internal 路径要求 X-Service-Token，并采用常量时间比较。它认证“谁在调用内部服务”，不是用户级授权的替代品。当前只绑定本机；公网部署还需要网络隔离、TLS 和专门的秘密管理。

练习：用 employee 和 hr 分别访问同一份 IT 文档、工单与会话；不要只比较菜单，要观察实际接口是否拒绝越权。阅读顺序：SecurityConfig → AuthService → DocumentService / TicketService → ConversationService → Python schemas 与 repository。

5. PostgreSQL、JPA 与 Flyway：把业务规则变成可靠数据

5.1 Controller、Service、Repository 的分工

ApiController 接收请求并调用服务；Service 验证角色、状态和业务规则；BusinessRepository 封装 EntityManager、事务和锁。Api.java 定义 DTO 与枚举，Entities.java 表示数据库实体。当前 Repository 是自行封装的 JPA 访问层，不是继承 Spring Data JpaRepository 的接口。

接口返回 DTO 而不直接返回 ORM 实体，可以控制字段暴露，避免把密码摘要、内部字段和持久化关联带给浏览器。统一成功响应是 {code:200,message:"success",data:...}，错误仍使用真实 HTTP 状态，不能所有异常都返回 HTTP 200。

5.2 事务的作用

“确认草稿”和“创建对应工单”应作为一个业务决定记录下来。事务使相关数据库变更共同提交或共同回滚；数据库锁防止并发请求各自认为“还没创建”；唯一约束是持久化层最后一道防线。

但 Java 事务不能自动回滚 Python 已经执行的 HTTP 请求，因此事务完成后再把业务结果交给图恢复，并对这一步设计安全重试。不要用一个数据库事务包住缓慢云模型调用，长期占用连接与锁。

5.3 数据库迁移为什么要进 Git

Flyway 按版本应用建表和增量脚本。以后新增字段，应新增迁移文件，不应只在本机手工改表后要求别人猜结构。代码升级和数据结构升级必须可追踪。

本项目删除补偿使用持久化清理标记，V2 迁移引入了对应字段。它是一个很好的例子：恢复机制不只是定时器，还需要能跨重启保存“仍有哪些工作没完成”。

练习：阅读迁移目录与 Entities.java，对照找出用户、会话、文档和工单的关系；解释哪些字段来自用户、哪些由服务端决定。不要为了练习删除现有数据卷。

6. 文档入库：S3、解析器、分块器与 Redis Streams

6.1 为什么原件与分块分开保存

RustFS 提供 S3 兼容接口，Python 通过 boto3 保存文件原件。PostgreSQL 保存可检索文本、向量、版本和任务信息。原件用于下载和重新处理，分块用于检索；两者用途和生命周期不同。

对象键使用 documents/{文档ID}/{版本}/{随机ID} 一类结构，避免同名文件覆盖别人的原件。下载仍经 Java 校验权限，不能把对象存储凭据或内部路径直接发给浏览器。

6.2 一次上传的完整过程

Java 校验管理权限、目标部门、扩展名与大小限制。目前最多 10MB，接受 txt、md、pdf、docx。Python 保存原件后，在数据库事务中登记当前版本与 ai_jobs 任务。上传返回 QUEUED，文档随后进入 PROCESSING，成功后成为 READY，解析失败则显示 FAILED 与安全错误说明。

数据库中的待投递任务是 outbox。它把“需要处理这个版本”的事实先持久化，再由 worker 投递 Redis Stream。数据库提交成功而 Redis 暂时不可用时，可以后续补投，不必要求两个系统瞬间同时成功。

6.3 Streams 的四个概念

概念本项目中的意义
Streamai:ingest，保存任务消息
Consumer groupai-indexers，组织消费与待确认消息
Pending已交给消费者但尚未 ACK 的消息
ACK数据库处理完成后确认消息，不等于删除业务任务事实

当前 worker 对超过 120 秒未确认投递完成的任务支持再次分发，通过 XAUTOCLAIM 接管空闲至少 30 秒的 pending 消息；失败尝试次数持久化，最多 3 次。每个任务使用 PostgreSQL advisory lock，防止重复消息并发执行、重复消耗尝试次数。

消息系统提供的重点是可重试投递。消费者必须按 documentId、version 和任务完成状态做幂等；已完成的消息再次出现时直接确认。不要把“有 ACK”说成端到端 exactly-once。

6.4 文本提取与切块

TXT / Markdown 按文本处理，PDF 使用 pypdf 提取文本，DOCX 使用 python-docx 读取段落和表格。扫描图片 PDF 尚无 OCR，不能期待解析器自动识别截图文字。解析器还有输入规模限制，避免压缩文档展开或异常页面耗尽资源。

RecursiveCharacterTextSplitter 的当前参数是 chunk_size=900、chunk_overlap=140，单位为字符。块过大可能混入无关内容和增加上下文成本；块过小容易切断步骤和条件。重叠用于保留边界附近语义，但也会增加重复和存储量。

这个参数是当前实现选择，不是通用最优值。调参应该用同一批有答案标注的问题比较命中情况，而不是看到别人用 1000 就认定必须改成 1000。

6.5 Embedding 失败不等于文本完全不可用

未配置 Embedding 时，文本仍可建立关键词索引。配置了模型但向量化失败时，也可降级为 keyword 模式并给出安全提示。READY 表示当前版本可用于已有检索能力，indexMode 才告诉你是不是具有向量。

练习：上传一份含“VPN E809”的 Markdown，观察状态和分块数量，再用不同问法检索。记录当前 indexMode；没有真实向量时，不把命中结果解释为语义召回。

7. LangChain：在项目里连接模型与业务组件

7.1 具体用了哪些部分

models.py 用 init_chat_model 创建聊天客户端，用 OpenAIEmbeddings 创建向量客户端；graph.py 用 SystemMessage、HumanMessage 表达提示消息，用 @tool 为草稿函数定义工具接口；ingestion.py 使用 LangChain 文本切分器。

这不是“引入一个依赖就算会 LangChain”。你需要解释每种抽象对应哪项业务工作，以及输入输出是什么。流程的暂停和恢复由 LangGraph 承担，数据库权限由 Java 和 Python 仓储承担，LangChain 不会替你自动解决这些问题。

7.2 聊天客户端

models.py 的核心配置如下，代码为实际实现摘录：

return init_chat_model(
    model_provider="openai",
    api_key=settings.agent_llm_api_key,
    base_url=settings.agent_llm_base_url,
    model=settings.agent_llm_model,
    temperature=0,
    timeout=45,
    max_retries=1,
)

这里的 provider 代表所用适配协议，实际请求目标由 base_url 决定。temperature=0 用来减少采样变化，不能保证没有幻觉或每次字节级相同。timeout 控制等待上限，重试也可能增加延迟和费用。

7.3 Prompt 的职责与局限

SystemMessage 要求只根据本次授权原文回答、使用编号引用、忽略原文中改变规则的指令、不要声称创建工单。HumanMessage 包含本次问题和编号证据。上传的文档是数据，不是能够改变系统权限的指令。

这些提示提高行为约束，但不是安全隔离本身。即使模型完全不遵守提示，也不应获得其他部门的原文或直接写入工单表，因为这些能力在调用模型之前已经被程序边界限制。

7.4 两种回答模式

没有聊天模型时返回“仅检索，未调用模型”与原文；配置了模型但没有授权证据时也不调用模型。真实模型请求失败或引用校验失败时返回安全错误，不偷偷生成一段假答案充当成功。

问答返回 mode="retrieval-only" 或 "llm"，前端据此展示状态。模型配置状态、索引模式、回答模式是三个不同维度：配置齐全不等于调用成功，keyword 索引也可能给聊天模型提供词面检索证据。

练习：在 graph.py 找到“没有 model”和“没有 sources”两个分支，解释它们为何都不调用模型。随后在测试中使用替身验证有证据时的输入消息；单元测试不需要消耗云模型额度。

8. RAG 与 pgvector：从问题找到当前有权看的证据

8.1 RAG 的最小闭环

离线阶段：文档 → 解析 → 分块 → Embedding → 保存文本与向量。在线阶段：问题 → 关键词与查询向量 → 授权范围内召回 → 合并排序 → 把证据交给模型 → 返回回答和引用。

RAG 不是把整个知识库直接塞进 Prompt。检索决定模型看到了什么；没有召回关键证据，后面的生成通常无法补救。因此要分别检查解析、检索和生成，避免所有问题都归因于“模型不够强”。

8.2 当前关键词检索怎样做

retrieval.py 将英文与数字标识提取为词项，并对连续中文取相邻双字片段，最多保留 32 个去重词项。repository.py 用匹配词项数量对候选分块排序，取最多 24 个。

这能让 E809、VPN 等专有标识参与检索，但属于轻量词面规则，不是 Elasticsearch、BM25 或成熟中文分词器。它适合当前演示数据规模，复杂同义词和噪声场景需要额外评估。

8.3 向量检索与 RRF

ai_chunks.embedding 使用 vector(1024)。查询向量有效时，SQL 通过 pgvector 的余弦距离运算符 <=> 排序，取最多 24 个语义候选。当前没有配置 HNSW/IVFFlat 近似索引，不应宣称已经完成 ANN 调优。

两路候选按文档、版本和块索引去重，再用 RRF 融合：每一路排名为 r（从 1 开始）的贡献为 1 / (60 + r)，同一块的贡献相加，最后最多返回 6 个合法来源。

RRF 解决的是两路分数刻度不同的问题，不把“词项命中数”和“余弦距离”直接相加。它不需要这两种原始分数可比，但常数、候选数和最终数量仍需要用数据验证。

8.4 权限过滤不能拖到生成之后

Java 首先计算可访问文档 ID，Python 再与实际索引元数据、当前版本和 READY 状态取交集。未授权内容不能先进入模型，再要求模型“不要输出”。过滤也不应只发生在前端展示阶段。

在模型生成期间，文档可能更新或删除，因此 Python 返回前检查来源是否仍是当前版本，Java 还要以自己的权威元数据重新检查。历史消息读取时也会重新检查来源；如果已经撤权或过期，整条相关助手回答正文与引用一起遮蔽，避免正文残留敏感信息。

8.5 引用校验能保证什么

当前引用校验要求答案含 [1] 这样的编号，且编号在本次 sources 范围内；来源还绑定 documentId、version、chunkIndex 和原文。它能发现不存在的引用与过期来源，却不能证明每一句结论都被原文语义支持。

练习：问一个知识库没有答案的问题，再更新一份已被引用的文档，重新打开旧会话。把观察分成“是否命中”“引用是否合法”“答案是否被支持”三项，不把它们合成一个模糊的准确率。

9. LangGraph：让工作流可以暂停与恢复

9.1 为什么普通函数链不够

如果只是 retrieve() 后执行 answer()，普通函数就够用。当流程需要等待人类确认，且关闭网页或重启服务后还能继续，就需要保存当前状态和执行位置。LangGraph 在本项目中解决的是这个问题。

状态图为：START → retrieve → answer；不需要工单时到 END，需要时进入 draft → approval → finish → END。requestTicket 来自用户显式选择，图按固定规则路由。当前不是模型自主决定调用哪个工具的 ReAct Agent。

9.2 State、node、edge、checkpoint

概念本项目例子要理解的意义
Statequestion、sources、proposal、decision、trace节点之间传递的结构化状态
Noderetrieve、answer、draft、approval、finish一步可说明职责的计算
Edgeanswer 后按 requestTicket 分流明确业务路径
CheckpointerPostgreSQL PostgresSaver保存状态和执行进度
thread_iduserId:conversationId区分属于不同用户的图执行

graph.py 的实际构图片段：

graph.add_edge(START, "retrieve")
graph.add_edge("retrieve", "answer")
graph.add_conditional_edges(
    "answer", lambda s: "draft" if s["requestTicket"] else END
)
graph.add_edge("draft", "approval")
graph.add_edge("approval", "finish")
self.graph = graph.compile(checkpointer=checkpointer)

9.3 @tool 与草稿

draft_ticket 是 LangChain 工具，当前按确定性规则生成草稿：标题来自问题前 100 字符，描述截取到 4000 字符，优先级 MEDIUM，并生成草稿 UUID。工具只产出可审核数据，不创建业务工单。

这里使用 @tool 是为了明确工具描述和输入输出。代码由 draft 节点显式调用工具，而不是把工具绑定给模型自由选择。简历中可以写“LangChain 工具封装”，不能写成“LLM 自主规划与多工具调度”。

9.4 interrupt 与 resume

approval 节点用 interrupt 返回草稿并暂停；用户点击确认后，Java 完成业务事务，Python 再执行 Command(resume=decision)。finish 节点只报告 Java 返回的工单号或取消结果。

decision = interrupt({
    "proposal": state["proposal"],
    "message": "请在Java业务服务中确认或拒绝工单草稿"
})
# 收到可信业务结果后恢复图：
result = self.graph.invoke(Command(resume=decision), config)

中断节点恢复时可能重新执行，所以不要在 interrupt 之前放没有幂等保护的扣款、发信或创建工单等操作。本项目把业务副作用放在 Java 事务中，approval 节点只接收决定。

9.5 保存历史不等于模型记忆

PostgreSQL checkpoint 用于流程恢复，Java 消息表用于界面历史。每个新问题会重置 sources、proposal、decision 等状态，并使用当前权限重新检索。模型不会自动看到之前助手正文，因此目前不能把“那第二步呢？”当作已实现的上下文追问能力。

练习：产生待确认草稿后重启应用，再打开会话确认；然后重复确认，检查工单 ID 没有变化。阅读 chat、pending_state、confirm 三个方法，解释它们分别处理新问题、丢失响应恢复和人工决定。

10. 工单状态机与幂等：让重试不会多办一件事

10.1 明确允许的状态转换

OPEN → IN_PROGRESS → RESOLVED → CLOSED。处理员或管理员可以接单与解决，解决时必须填写说明；创建者或管理员可以把已解决工单关闭，并提供 1—5 分评价。跨状态跳转返回 409，越权返回 403。

状态机不一定需要额外框架。当前通过枚举、显式转换检查、数据库事务和行锁完成，规模清晰时便于阅读和测试。评论是协作记录，不应悄悄绕过状态规则。

10.2 为什么确认按钮禁用还不够

用户可能重复点击，网络客户端可能重试，服务端也可能在提交成功后丢失响应。前端按钮只能减少误操作，不能成为“只创建一次”的唯一保证。

TicketService 根据创建者和 idempotencyKey 查询已有记录。相同键、相同内容返回同一工单；相同键却携带不同内容返回冲突。创建时锁定创建者对应记录，并在事务内检查与保存。

10.3 两层幂等分别解决什么

Java 的事务与持久化记录保证业务工单不重复。Python 的确认回执记录 proposalId、decision 与 answer，保证相同决定重复恢复时返回同一结果，矛盾决定返回 409。

checkpoint 只知道图走到哪里，不能独自保证外部业务副作用恰好一次。持久化幂等键和实际业务事务也不能替代工作流的暂停状态。面试中要把这两个问题分别讲清。

练习：在正常关闭前，尝试 employee 直接把 OPEN 改成 RESOLVED，或由其他员工访问工单。然后使用同一确认结果重试，核对数量和 ID。不要把“接口返回成功”当成唯一证据。

11. React 与接口协作：让用户知道系统正在做什么

App.tsx 组织登录、导航与工作台；Documents.tsx 管文档与索引状态，处理中约每 4 秒轮询；Assistant.tsx 管会话、证据与确认；Tickets.tsx 管状态和评论；Management.tsx 展示用户与依赖健康状态。

api.ts 统一处理 token、JSON envelope、下载与安全错误；permissions.ts 控制可见操作；ui.tsx 复用对话框与交互。TypeScript 让字段与组件契约更明确，但不能替代运行时后端校验。

几个必须表达清楚的界面状态：文件已上传但尚未 READY；当前回答仅检索；草稿正在等待确认；请求结果不确定，需要恢复状态；服务不可用；引用因版本或权限变化不再展示。界面不能只剩一个通用“失败”。

当前前端调用 Java，不直接访问 Python。这样用户身份、资源授权和消息持久化都经过同一业务入口。浏览器显示的执行 trace 来自受控流程，不是模型的隐藏推理过程。

练习：同时打开浏览器 Network 和页面，沿一次提问找到 Java 请求、mode、sources 与 proposal，再对照 TypeScript 类型和后端 DTO。能从画面解释到请求字段，才算理解前后端联调。

12. 故障恢复：项目最值得讲的四类问题

12.1 文档撤权后，旧答案仍泄露内容

只删除引用链接不够，助手正文可能已经包含原文。当前读取历史时重新验证来源，一旦不再满足权限或版本要求，遮蔽整条相关回答及引用。回归方式是将 PUBLIC 文档改成 HR 私有，再以 IT 员工读取历史。

这说明权限不只是检索 SQL 上的一条 WHERE；持久化的派生内容同样需要考虑撤权。

12.2 Python 已暂停，Java 没收到草稿响应

网络可能在 Python checkpoint 已保存、Java 消息尚未保存之间断开。此时重发新问题会发现图仍在等待确认。当前增加认证的 /internal/chat/state，只读取得该用户会话的待确认状态，不调用模型。

Java 在会话锁下恢复缺失消息和草稿，并重新校验来源；重复恢复不重复插入。它解决的是“不确定上次有没有成功”，不能简单用再次执行整个模型请求替代。

12.3 删除文档时 Python 恰好离线

Java 先持久化删除状态，使用户立即失去访问权限，并记录仍需清理。后台约每 60 秒重试 Python 删除，成功才标记清理完成。这样服务重启后也知道未完成工作。

Python 使用删除墓碑拒绝旧任务重新发布，通过 ai_gc 持久化队列清理对象存储。可见性立即撤销与物理清理最终完成是两个时刻，都要有验证。

12.4 旧版本任务晚于新版本完成

如果版本 1 处理很慢，版本 2 已经上传，不能让版本 1 最后完成时覆盖新索引。发布分块时在数据库锁内校验当前版本和删除状态，只有仍有效的任务可以原子替换分块。

版本检查与写入必须组成一个不可被并发更新穿透的操作。仅在解析开始时检查一次版本，不足以防止处理中发生的更新。

12.5 仍需承认的缺口

S3 保存原件后、数据库登记前如果进程崩溃，可能留下没有任务记录的孤立对象。正常删除与离线补偿已验收，但这个跨系统缝隙仍需对象生命周期或定期盘点补足。能够解释未覆盖的窗口，比把系统描述成“绝对不会丢失”更可靠。

16. 面试与简历：用真实实现回答追问

16.1 一分钟介绍

“我做的是一个企业知识助手与工单协作平台。Java 负责身份、部门权限和工单事务；Python 用 LangChain 接模型，用 LangGraph 组织检索、回答、草稿与人工确认；文档经 Redis Streams 异步解析入库，原件保存在 S3 兼容存储，分块和向量在 PostgreSQL。我的重点是权限贯穿检索和历史回答、工作流重启恢复，以及确认重试不重复建单。当前完成了本机闭环和异常验收，真实云模型质量还需要独立评测。”

16.3 高频追问与回答要点

问：LangChain 和 LangGraph 的区别是什么？答：本项目用 LangChain 的模型、消息、工具和切分组件；LangGraph 负责节点路由、状态和中断恢复。它们协作，但不替代权限与业务事务。

问：为什么需要人工确认？答：生成草稿与执行业务操作的风险不同。用户确认后 Java 才创建工单，模型不能把自然语言“已创建”变成事实。

问：checkpoint 能否保证只创建一次？答：不能。它保存执行状态；外部副作用仍要依赖业务事务、幂等键、唯一约束和可重试结果。

问：Redis 消息重复怎么办？答：任务事实先落库，消费者按任务和版本检查，使用任务锁避免并发，完成后 ACK，重复已完成任务只确认；同时拒绝过期版本发布。

问：为什么用 pgvector 而不是独立向量库？答：当前规模下复用 PostgreSQL 降低组件数量，并便于元数据过滤。现版是精确向量检索，没有对大规模 ANN 性能下结论。

问：权限为何不能交给 Prompt？答：Prompt 是行为约束，不能防止程序把未授权原文传给模型；必须在检索前过滤，并在返回和历史读取时校验。

问：你们是不是完整多轮 Agent？答：当前是固定可恢复工作流，显式 requestTicket 分支；聊天历史持久化，但旧回答不作为模型上下文，也没有自主多工具规划。

问：RRF 为什么不直接相加原始分数？答：词项命中数和向量距离量纲不同，RRF 使用排名贡献融合，仍需用固定评测集验证参数。

问：如何证明 RAG 效果？答：区分检索命中、引用合法、事实支持、权限安全与成本；当前小样本只证明 keyword 功能回归，不能代替真实企业效果评估。

问：最有价值的一次修复是什么？答：可选历史撤权或丢失草稿响应。按“触发条件 → 错误结果 → 原因 → 修复 → 真实回归证据”讲，别只说加了 try/catch。

问：项目从哪里来？答：参考公开项目的 RAG 与异步处理思路，按企业知识和工单场景独立实现，AI 层改为 Python LangChain/LangGraph，并完成权限、事务与恢复链路。说明工具辅助与自己实际掌握、修改的部分，保留来源说明。

17. 后续扩展顺序与资料索引

17.1 先补证据，再加组件

第一步完成云聊天和 Embedding 的少量受控验收，记录模型、维度、样本、延迟与费用。第二步扩大固定评测集，找出实际失败类型。第三步根据失败再选择改造：专有名词匹配不足考虑更好的词面检索；候选相关但排序差考虑 Reranker；指代追问不足考虑权限受控的查询改写；首屏等待长考虑 SSE。

新增 HNSW 前先量化数据量、精确检索延迟与召回损失；新增多 Java 实例前先替换进程内会话协调假设并验证并发；增加 OCR 前先定义文件规模和解析资源限制。这些都是计划，不是本版本已有功能。
