## Important findings

1. **P1 — Revoked/deleted document text remains exposed through conversation history.** `backend/src/main/java/com/example/helpdesk/ConversationService.java:79–82` returns stored `m.content` unchanged while filtering only its source list. Reproduce: an IT employee asks about a PUBLIC document; the retrieval-only answer includes its original text; an administrator replaces it with an HR-only version or deletes it; the employee GETs the existing conversation. Sources are filtered, but the old source text remains in assistant content. This bypasses the intended current-source boundary and also serves superseded content without its provenance. Hide the entire evidence-derived historical answer whenever any stored source is no longer authorized/current. Cover replacement, department visibility changes and deletion in regression tests.

2. **P2 — Deletion during Python outage permanently loses the cleanup operation.** `backend/src/main/java/com/example/helpdesk/DocumentService.java:206–218` marks the document inactive, saves it, then ignores an unsuccessful Python DELETE. Reproduce: upload/index a document, stop Python, DELETE through Java, restart Python. Java has already returned success and no longer lists the document; repeating DELETE fails its active-document lookup. There is no persistent cleanup retry, so Python chunks/registry and the S3 original remain indefinitely. Java authorization still blocks new browser access, but the promised deletion of originals/index is not fulfilled. Persist cleanup intent and retry after recovery/restart; verify active access is revoked immediately and physical cleanup eventually occurs.

3. **P1 — A lost draft response leaves the conversation permanently unconfirmable.** `ai-service/app/graph.py:148–164` durably saves the graph interrupt/proposal before returning; `backend/src/main/java/com/example/helpdesk/ConversationService.java:93–113,156–161` saves Java's pending proposal only after that response arrives. Reproduce: interrupt Java or the internal response connection after Python checkpoints a ticket draft but before Java commits its messages/pending proposal, then retry the request after recovery. Python refuses further chat with 409 because it has a pending proposal; Java history has no proposal, and Java confirm rejects it. Restart preserves the disagreement. Add safe replay/reconciliation for a pending graph response, bound to conversation owner and original request; do not silently accept a different question. Confirm/rejection retry logic after Java has saved a decision is otherwise structured durably.

4. **P2 — Browser smoke can incur cloud charges before its opt-in check.** `scripts/browser-smoke.cjs:41` uploads a document before the check at `:61–62`; that check only searches for a chat-model UI label. With embedding credentials configured, upload already invokes cloud embeddings. An embedding-only setup bypasses the later check entirely, and a still-loading UI label is not a reliable configuration test. Read authenticated `/api/system/status` and require both configuration flags to be explicitly known and false before upload/chat, unless `--allow-model` is provided. Test this guard with fake status responses; no cloud invocation is needed.

## Positive checks and remaining verification

The source contains real S3 storage, Redis Streams ingestion with a durable PostgreSQL job registry, version-checked atomic index replacement, real model adapters, PostgreSQL LangGraph checkpoints, owner-qualified graph threads, current request document whitelists, and explicit retrieval-only answers. It does not substitute fake production model responses. Role-aware UI actions match backend ownership/department transitions. Windows process management checks command ownership and creation time; application and Compose ports bind loopback.

The Java schema-isolation startup correction and Python no-evidence mode correction were being implemented during review. Full real-infrastructure/browser/restart verification belongs to the parent task; do not interpret existing happy-path results as coverage for the four failure paths above.
